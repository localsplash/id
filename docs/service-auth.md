# Aida service-to-service authentication

How `id` proves who it is to other Aida services, and how it decides whether
to believe them.

Design: `localsplash/AidaInfrastructureSetupInstructions#10`, which fixes the
algorithm, the key encoding, the identity key, and what a signature has to
cover. It does not name the HTTP headers or fix the byte order they are signed
in, and no peer had implemented its side when this was written — so **this
document defines those, and this service is the first implementation of them.**
A peer that follows this page will interoperate. Changes here are changes to a
contract, not to one service.

## Identity

An application is `(application_name, environment)`. Never a hostname:
hostnames change with ingress, replicas share one identity, and a service
reachable under two names is still one application.

`id` registers as `application_name = id`, `environment = AIDA_ENVIRONMENT`
(defaulting to `NODE_ENV`).

## Keys

| | |
| --- | --- |
| Algorithm | Ed25519 |
| Private key | `AIDA_APP_PRIVATE_KEY` — base64 of the PKCS#8 DER, one line, no PEM header or newlines |
| Public key | base64 of the SPKI DER, published to `aida_application.public_key` |

Generate one with `npm run keygen`. The service never generates or persists a
private key outside development: a key file does not survive a container
rebuild without a volume, and a volume that must be right in every environment
forever fails silently when it is not.

Absent in production, the process **refuses to start** and names the variable.
Absent in development, it generates an ephemeral key and warns that the key
changes on every restart.

Replicas read the same environment, hold the same key, and publish the same
public key. There is nothing for them to overwrite.

### This key has nothing to do with user sessions

Verified while implementing, and worth stating plainly because the failure it
rules out would be a mass logout:

A session is 32 random bytes generated by `crypto.randomBytes`, stored in
`id_tbl_Session`, and validated by looking the row up and checking
`dtRevoked IS NULL` (`src/store.ts`). No session value is derived from,
signed by, or verified against `AIDA_APP_PRIVATE_KEY`, and no code outside
`src/aida/` reads that variable.

**Changing the service key signs nobody out.** Rotating it is an ordinary
config change: set the new value, restart, and the new public key publishes
itself.

## The registry

Two tables in the shared `AidaOffice` base. `id` finds or creates them so it
can come up whether or not AidaControl's schema automation has run, and never
creates the base — the settings store owns that decision.

### `aida_application`

| Column | Type | Meaning |
| --- | --- | --- |
| `application_name` | text | Half of the identity |
| `environment` | text | The other half |
| `public_key` | long text | base64 SPKI DER, current key |
| `key_version` | number | Incremented on each rotation |
| `previous_public_key` | long text | The outgoing key during a rotation overlap |
| `previous_key_version` | number | Its version |
| `previous_key_retired` | checkbox | Tick to stop accepting the previous key |
| `enabled` | checkbox | Untick to refuse this application everywhere |
| `last_seen_at` | datetime | Refreshed each registration pass (every 60s) |
| `notes` | long text | For operators |

The registry holds **no secret**. A read of it lets you verify signatures,
never produce them.

### `aida_system_setting`

| Key | Value |
| --- | --- |
| `auto_enroll_applications` | `true`, `false`, or a per-environment map such as `{"production": false, "staging": true}` |
| `expected_applications` | `["aida-control", "id", "aida-admin"]` |

While enrolment is open, an application registering for the first time creates
its own row. Once every name in `expected_applications` has a registered,
enabled row for an environment, enrolment closes **for that environment only** —
staging finishing its rollout must not close the door on production.

The expected list does double duty: **appending a name re-opens enrolment**, so
bringing a new service online is one cell edit and the door shuts again by
itself. `/readyz` reports which expected applications have not yet registered,
which is what makes a name that never arrives visible rather than silently
holding the door open.

## The wire format

Six headers on every signed request:

| Header | Value |
| --- | --- |
| `X-Aida-Application` | caller's `application_name` |
| `X-Aida-Environment` | caller's `environment` |
| `X-Aida-Key-Version` | the `key_version` it signed with |
| `X-Aida-Timestamp` | unix seconds |
| `X-Aida-Nonce` | 16–128 characters, unique per request |
| `X-Aida-Signature` | base64 Ed25519 signature over the canonical string |

The canonical string is eight fields joined with `\n`, no trailing newline:

```
AIDA-SVC-v1
POST
/internal/v1/whoami?x=1
<lowercase hex sha256 of the raw request body>
<unix seconds>
<nonce>
<application_name>
<environment>
```

- **Line 1** is a version tag, so a future v2 signature can never verify as v1.
- **Line 2** is the method, upper-cased.
- **Line 3** is the path with its query string, exactly as it appears on the
  request line. No scheme or host — those change with ingress and proxies.
- **Line 4** is the hash of the raw bytes received. Re-serialising a parsed
  body would not reproduce the caller's spacing or key order, and every
  signature would fail for reasons nobody could see. Empty body hashes the
  empty string.
- **Lines 7–8** put the caller's identity inside the signature, so a request
  captured in staging cannot be relabelled and replayed against production —
  the same application name there is a different row with a different key.

Every field is also a header, and the verifier rebuilds the string from the
request rather than trusting anything the caller sends as a blob.

### Verification, in order

1. Headers present and well formed, else `malformed`. Nothing here reads the
   registry, so a garbage request costs no round trip.
2. Timestamp within **±300 seconds**, else `stale_timestamp`.
3. A row for `(application_name, environment)`, else `unknown_application`.
   A cache miss is retried once against a fresh read, so a peer that enrolled
   a moment ago is not refused.
4. `enabled` is ticked, else `disabled`.
5. The signature verifies against **any unretired key on the row** — the
   current one or an unretired previous one — else `key_mismatch`. A failure
   forces one fresh read of the row, so a peer's rotation takes effect here
   without a restart or waiting out the 30-second cache.
6. The nonce has not been used, else `replayed_nonce`. This is checked **last**,
   so a request that fails its signature cannot burn a nonce the legitimate
   caller is about to use. Nonces are stored in MySQL, not process memory, so
   replicas do not each accept the same replay once.

### What the caller is told

`401 {"error":"unauthorized"}`, or `503 {"error":"unavailable"}` when the
registry itself could not be read. **Never which check failed** — that would
hand a caller a probing oracle. The category, the presented identity, and the
row to open go to the local log, where the operator already has access.

## Endpoints

`GET /readyz` — unauthenticated, carries no secret. `200` when this service is
registered and enabled, `503` otherwise, with the reason and the row:

```json
{
  "ready": false,
  "application": "id",
  "environment": "production",
  "reason": "disabled",
  "detail": "this application is registered but its `enabled` box is unticked…",
  "row": { "base": "AidaOffice", "table": "aida_application",
           "application_name": "id", "environment": "production" },
  "pendingApplications": ["aida-admin"]
}
```

Readiness is separate from `/healthz` on purpose. The process being up and
peers being able to call it are different questions, and during an incident
"why is sign-in failing" should be answerable from one HTTP call.

Because it is unauthenticated, the body carries the failure **category** and
the row — both of which are on this page anyway — and never raw backend error
text. The underlying error goes to the service log.

`GET /internal/v1/whoami` — signed. Echoes the verified caller. It exists as a
conformance target: a peer that gets `200` here has its signing right.

## Rotation

1. `npm run keygen`, put the new value in the environment, restart.
2. The service publishes the new key, moves the old one to
   `previous_public_key`, and bumps `key_version`. Peers accept both.
3. Once every peer has re-read the row — at most one cache interval, and a
   `key_mismatch` forces a read anyway — tick `previous_key_retired`.

To revoke a compromised key immediately, untick `enabled` or clear
`previous_public_key` and retire it. The application is uncallable until it
publishes a new one, which is the intended trade.

## Failure behaviour on the auth path

`id` is the service everything else authenticates through, so two choices here
differ from the other Aida services:

- **An unreachable registry at startup leaves this service unready**, not
  started-and-failing at the first call. A rollout that cannot reach NocoDB
  stops instead of half-working. Registration retries every 60 seconds, so the
  service becomes ready on its own once NocoDB returns — no restart.
- **The replay store failing open.** If MySQL cannot record a nonce, the
  request is allowed rather than refused. Everything else has already
  passed — signature, freshness, enabled state — so the exposure is a replay
  inside a 300-second window during a database outage, against the alternative
  of taking sign-in down for everyone. Stated here because it is a deliberate
  trade and not an oversight.
